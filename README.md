# MGH-900: GitHub Foundations

**Course date:** September 10, 2026  
**Format:** One-day, practice-first workshop

This repository is the working space for MGH-900. By the end of the course, learners will be able to use GitHub to create and organize work, make focused changes, collaborate through pull requests, track work with issues and Projects, and understand the role of GitHub Actions.

## Learning outcomes

Learners will be able to:

- Create or configure a repository with a useful README and .gitignore.
- Explain the relationship between files, commits, branches, and the default branch.
- Make a small change on a branch and open a pull request.
- Review, discuss, and merge a pull request safely.
- Create actionable issues and organize them in a GitHub Project.
- Read a basic GitHub Actions workflow and interpret its result.
- Apply practical habits: small commits, clear descriptions, and no secrets in source control.

## Before class

- Sign in to a GitHub account you can use for practice.
- Open this repository and check that you can view the files.
- Bring a small, non-sensitive project idea to use in the final challenge.
- GitHub's web editor is enough for this workshop; Git and GitHub Desktop are optional.

## How to use this repository

1. **Read the lab objective** before starting.
2. **Work in a personal fork or practice repository** unless the instructor tells you to use a shared repository.
3. **Complete the success check** at the end of each lab.
4. **Use the pull request template** when opening a PR so your explanation is part of the work.
5. **Treat the final challenge as a small, complete workflow**, not a large coding project.

## Working safely

Never commit passwords, API keys, private customer data, or other secrets. If a secret is accidentally committed, removing the file is not enough: revoke or rotate the secret immediately, then ask the instructor for help.

## Definition of done

You are ready to leave when you can point to:

- one meaningful commit;
- one branch that is not the default branch;
- one pull request with a clear description;
- one issue that another person could act on;
- one Project view or board with work organized; and
- one successful Actions run you can explain in plain language.
